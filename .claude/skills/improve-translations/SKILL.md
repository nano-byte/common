# Improve translations

## How translations work in this repo

- `src/Common/Properties/Resources.resx` is the English source and the only localized resource file. Never edit it as part of this skill.
- `src/Common/Properties/Resources.<lang>.resx` is the committed, combined translation the build uses. It is generated by the monthly `.github/workflows/translate.yml` run (`MrMeeseeks.ResXTranslationCombinator`) from:
  - `Resources.<lang>.o.resx`: human translations pulled from Transifex (gitignored). Become entries with `<comment>Manually overriden.</comment>`.
  - `Resources.<lang>.a.resx`: DeepL output (gitignored, cached in CI). Used for keys without a human translation; become entries with `<comment>Automatically translated.</comment>`.
- DeepL fills gaps for `cs el es fr id it ja ko nl pl pt-PT ro ru zh`. `de`, `pt-BR` and `tr` are human-only. Unlike 0install-dotnet and 0install-win, no DeepL glossary is used here.
- Because the combined files are regenerated every month, **an improvement only survives if it is also uploaded to Transifex**. That is why step 6 exists.
- `.tx/config` maps the file to the Transifex resource `common` in the `0install-win` Transifex project (shared with Zero Install) and `pt-PT`/`pt-BR` to `pt_PT`/`pt_BR`.

NanoByte.Common is a general-purpose library. Its strings are shown by many applications (Zero Install, OmegaEngine, ...) in CLI output, GUI dialogs, progress/task names, exception messages and update/error-report UIs. Translations must therefore stay neutral: no Zero Install or other app-specific terminology, even where it would read more naturally in one app.

Helper scripts live in `.claude/skills/improve-translations/scripts/` (PowerShell 5.1 and 7 compatible). Run them from the repository root.
When writing your own ad-hoc PowerShell for this skill, keep in mind:
- Windows PowerShell 5.1 reads `.ps1` files without a BOM as ANSI, which garbles non-ASCII literals (umlauts, CJK). Keep scripts ASCII-only and build non-ASCII characters from char codes (e.g. `[char]0x00AB`), save them with a UTF-8 BOM, or run them with `pwsh`. Don't rely on `\uXXXX` escapes written through file-editing tools, because they may be turned into literal characters.
- Typographic quotes (`“ ” „ ‘ ’`) are string delimiters in PowerShell, so don't put them in inline commands; use char codes instead.
- In Windows PowerShell 5.1, `ConvertFrom-Json` emits a JSON array as a single object. Unroll it with `| ForEach-Object { $_ }` before grouping or counting.
- `-eq`/`-ne`/`-contains` ignore case. Use `-ceq`/`-cne` when comparing translations, or case-only fixes look like no-ops.
- Read JSON and `.resx` files with an explicit UTF-8 encoding (`Get-Content -Encoding UTF8` or `[IO.File]::ReadAllText`).
- Call the scripts in-process (`.\.claude\...\Script.ps1 -Languages fr,ja`), not via `powershell -File`, which passes `fr,ja` as a single string.

## Workflow

### 1. Determine scope

Parse the arguments into languages (file-name codes such as `fr`, `pt-BR`). There is only one project (`Common`), so `-Projects` can be omitted from all script calls.
- Languages default to **all** localized languages, including `de`, `pt-BR` and `tr`.
- Make sure the working tree has no uncommitted changes to `*.resx` files, so that `HEAD` is a clean baseline for detecting what this run changed. If there are, ask the user how to proceed.

### 2. Gather context

Dump the strings with the code that uses them into the scratchpad:

```powershell
.claude/skills/improve-translations/scripts/Get-TranslationContext.ps1 -Languages fr,ja -OutFile <scratchpad>/Common.txt
```

Options: `-Status Auto|Manual|Missing` to narrow down, `-Keys` for specific keys, `-MaxUsages` for more call sites. Read the output in chunks. Each block shows the English source, up to three usages with surrounding code, and every translation with its status (`auto`, `manual`, `missing`).

Also run the mechanical checks and include their findings in the review:

```powershell
.claude/skills/improve-translations/scripts/Test-Translations.ps1 -Languages fr,ja -CountStraySpaces
```

Besides errors for placeholder mismatches (including format specifiers such as `{0:0.00}`), it warns about missing access keys (`&`) and mismatched quote marks around placeholders. `-CountStraySpaces` adds the number of entries per file with the stray-space artifact described in step 3.

If a usage snippet is not enough to understand the string (e.g. it is passed through several layers, or concatenated with other strings), open the referenced file. Many strings are only used by consuming applications (e.g. generic button labels, `Resources.*` passed into tasks or exceptions by callers); judge them by their key name and wording, and keep them generic.

When reviewing many languages, work through them one at a time:
- Generate one context file per language (`-Languages fr -OutFile <scratchpad>/lang/fr.txt`).
- Collect the proposals as a JSON file per language in the format `Apply-Translations.ps1` expects (see step 5). Each entry needs `project` (`Common`), `key`, `status`, `old` copied exactly from the context file, `new`, and a short English `reason`. Check each file with `Apply-Translations.ps1 -WhatIf` before presenting it. Note the glossary and any systematic issues left unfixed. Those issues are worth passing on to the user.

### 3. Find poor translations

Review `auto` entries first; they are the most likely to be wrong. Review `manual` entries too, but only propose changes for clear errors, since they are human decisions.

Work out how each string is used from its code usage, e.g. exception message, progress/task name, UI label or button, question to the user, log message, CLI output. Then check for:

- **Meaning in context:** literal translations that pick the wrong sense of an ambiguous word (e.g. "file" as noun vs. verb, "download", "extract", "hash"/"digest", "handler", "task", "batch").
- **Terminology consistency:** build a per-language glossary from the existing `manual` entries for recurring concepts (tasks, downloads, archives, permissions, network, update, error report) and align `auto` entries with it. When you change a term, check the language's other strings for the same term. Use the platform's (Windows/.NET) standard UI terms for things like "OK", "Cancel", "Yes to all", "Details".
- **Things that must stay literal:** file names, environment variables, URLs, command-line option names, protocol and product names.
- **Placeholders and formatting:** every `{0}`, `{1}`, ... preserved; line breaks and leading/trailing whitespace preserved (strings may be concatenated or column-aligned in CLI output); quotes around placeholders following the language's conventions (watch out for DeepL artifacts like `«{0} »` with a stray space).
- **Grammar with placeholders:** the sentence must still be grammatical once `{0}` is substituted (e.g. gender/case agreement, word order for a file path vs. a name; counts vs. names).
- **Register and tone:** consistent formal/informal address within a language matching the manual entries; imperative vs. infinitive for buttons and menu items as is conventional for the language; no overly literal or verbose phrasing for short labels.
- **Neutrality:** no app-specific terminology (see above).
- **Untranslated or mixed-language text** that should be translated, and translations that are simply wrong or incomplete.

Errors that came up repeatedly in past runs of this skill in related repos, across many languages:
- **Count placeholders read as names:** in strings like "{0} items", DeepL often treats `{0}` as a label rather than a number.
- **Inverted meaning or direction:** "case insensitive" translated as "case sensitive"; "{0} of {1}" became "{1} of {0}".
- **First-person or instruction-style phrasing:** status messages written as "I downloaded…" or "Please open…" instead of descriptive text.
- **Stale manual entries:** some human translations were made from older English source texts and no longer match; compare meaning, not just wording.
- **Formatting artifacts:** DeepL artifacts such as backticks around placeholders, `l'{0} e`, and missing spaces (`{0}angefordert`); a lowercase sentence start or a capital mid-sentence after a placeholder.
- **Garbage:** placeholder text like `XXX` left in manual entries.

The stray-space artifact (`«{0} »`, `„{0} “`, `「{0} 」`, `{0} を`) may affect many `auto` entries (see the `-CountStraySpaces` output; it covers the quote cases, not spaces before particles like `を`). Fixing it turns each entry into a manual override that gets uploaded, so ask the user up front whether to fix it everywhere or only in entries changed for other reasons.

### 4. Propose and confirm

Present the proposals per language as a table: key, current text, proposed text, short reason (and whether the entry was `auto` or `manual`). Ask the user to approve, adjust or drop rows. Do not edit files before approval.

For large runs, ask the user up front which languages they want to review row by row; they may trust your judgment for languages they don't speak. Group repetitive rows into one table row listing the keys, so the table stays readable.

### 5. Apply

For each approved row, edit `Resources.<lang>.resx` with the Edit tool (do not reserialize the file with an XML library, so the combinator's formatting, UTF-8 BOM and LF line endings stay intact):
- Replace the `<value>` text, XML-escaping `&`, `<` and `>`.
- Set the entry's comment to exactly `<comment>Manually overriden.</comment>` (keep this spelling; it is what the combinator emits) if it is not already.
- Do not touch any other entry.

For many proposals, put them in a JSON file per language instead and apply them with the script. It does the same exact in-place replacement. It skips a proposal with a warning when:
- its `old` doesn't match the current value exactly (case-sensitive, including trailing line breaks);
- its `new` fails validation against the English source: it must keep the same placeholders, access key count, number of line breaks and leading/trailing whitespace, and must differ from `old` (case-sensitively).

```powershell
.claude/skills/improve-translations/scripts/Apply-Translations.ps1 -Path <scratchpad>/proposals/fr.json -Language fr [-SkipKeys Common/SomeKey] [-SkipValidation Common/OtherKey] [-WhatIf]
```

Run it with `-WhatIf` first and fix every proposal it warns about, e.g. a trailing line break dropped from `old` or an access key dropped from `new`. Use `-SkipValidation` only for intended differences, such as restoring a line break the translation was missing. Afterwards, `git diff --numstat` should show equal insertions and deletions per file, except where a line-break fix was intended.

Then validate the changed entries and the build:

```powershell
.claude/skills/improve-translations/scripts/Test-Translations.ps1 -Base HEAD
dotnet build src
```

Fix any errors before continuing. Review warnings and fix them unless they are intentional.

### 6. Upload changed entries to Transifex

Generate `.o.resx` files containing **only the manually overriden entries changed in this run** (compared against `HEAD`; use `-Base <commit>` if the changes are already committed):

```powershell
.claude/skills/improve-translations/scripts/Export-ManualOverrides.ps1
```

The script writes the files at the paths `.tx/config` expects, overwriting any stale local copies from earlier `tx pull`s. It prints:
- each file with its keys;
- the total number of entries per language;
- the push command, listing only the affected languages, so no other local `.o.resx` file is uploaded.

Partial files only update the keys they contain; other translations on Transifex are left alone. Check that the totals match the number of applied proposals.

Show the user the keys per language and the push command. **Ask for confirmation before pushing**, since this publishes the translations. The Transifex CLI reads the API token from `~/.transifexrc` or the `TX_TOKEN` environment variable; never ask for, print or store the token. If authentication fails, tell the user to set it up themselves.

After confirmation, rerun the script with `-Push`. It writes the same files, runs the printed command from the repository root and prints only the non-progress output of the CLI:

```powershell
.claude/skills/improve-translations/scripts/Export-ManualOverrides.ps1 -Push
```

The resource argument must be in the CLI's `<project>.<resource>` form (`0install-win.common`), which the script uses. The full `.tx/config` section name (`o:eicher:p:0install-win:r:common`) makes the CLI exit with code 1 and print nothing. If a push fails silently, `tx status` (same CLI, no network needed) shows which resources the CLI sees.

The CLI skips files whose remote translation is newer, e.g. because someone edited it on Transifex. Its status lines are cut to the console width (`[fr] - Skipping becau..`), so skips are easy to miss when running the command by hand. `-Push` collects them and lists each skipped language with its keys, plus a `--force` command for just those languages. Report the skipped keys to the user instead of forcing right away. If the user decides to force them, run the printed `--force` command while the generated files still exist. If the files are already removed, regenerate them first (with `-Base HEAD~1` if the changes are already committed), e.g. `-Push -Force -Languages <lang>`.

Afterwards remove the generated files so they cannot be pushed again by accident (use the same `-Base` as before):

```powershell
.claude/skills/improve-translations/scripts/Export-ManualOverrides.ps1 -Remove
```

### 7. Commit

Commit only the changed `Resources.<lang>.resx` files, e.g. `Improved fr and ja translations`. Do not push unless the user asks.
